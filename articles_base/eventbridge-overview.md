## Amazon EventBridge とは

AWS のサービス、自社アプリケーション、SaaS アプリケーションなどから発生する「イベント」を受け取り、あらかじめ定義したルールに従って Lambda や SQS などの送信先（ターゲット）へ振り分ける、サーバーレスのイベントバスサービスです。もともとは Amazon CloudWatch Events として提供されていた機能が拡張され、2019 年に EventBridge として独立したサービスになりました。

[Amazon EventBridge サービス概要](https://aws.amazon.com/eventbridge/)

[Amazon EventBridge ドキュメント](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-what-is.html)

[Amazon EventBridge よくある質問](https://aws.amazon.com/eventbridge/faqs/)

[Amazon EventBridge の料金](https://aws.amazon.com/eventbridge/pricing/)

イベント駆動アーキテクチャの中核となるサービスで、サービス同士を直接呼び出す代わりに、EventBridge を介して疎結合に連携させることができます。

## 構成要素

EventBridge は「イベントバス」「ルール」「ターゲット」という 3 つの要素で構成されています。

### イベントバス

イベントが流れる経路です。アカウントには自動的に用意される「デフォルトイベントバス」に加えて、用途ごとにカスタムイベントバスを作成できます。他の AWS アカウントやリージョンのイベントバスとイベントを共有することも可能です。

デフォルトイベントバスだけで運用することもできますが、あえてカスタムイベントバスを分けて作ることには、次のような実利があります。

- **ルールの見通しを保てる**：デフォルトイベントバスには EC2 の状態変化や GuardDuty の検出結果など、AWS サービスが発行する大量のイベントが常に流れ込みます。自社アプリケーションが発行する独自イベント（注文確定、ユーザー登録など）を同じバスに混在させると、ルールの数が増えるにつれてどのルールが何のためにあるのか把握しづらくなります。アプリケーション用・ドメイン用にバスを分けることで、ルールの見通しと保守性を保てます。
- **アクセス制御の単位を分離できる**：イベントバスにはリソースベースポリシーを設定でき、「どのアカウント・どのロールがこのバスにイベントを送信できるか（あるいはこのバスのルールを変更できるか）」をバス単位で制御できます。デフォルトバスに全チームが好きに書き込める状態に比べ、チームやサービスごとにバスを分けて権限を絞ることで、誤ったイベント発行や意図しないルール変更のリスクを抑えられます。
- **クロスアカウント共有の範囲を最小化できる**：他アカウントとイベントを共有する際、デフォルトバスを丸ごと共有すると、AWS サービス由来のイベントまで意図せず共有範囲に含めてしまいかねません。共有したいイベントだけをカスタムバスに集約しておけば、共有相手に渡す権限を必要最小限に絞れます。
- **障害・設定ミスの影響範囲を限定できる**：あるバスのルール設定を誤った場合でも、影響はそのバスに紐づくイベント・ルールに閉じます。デフォルトバス 1 つに全てを集約していると、1 つのルールの不具合がシステム全体に波及するリスクが高まります。
- **ドメイン単位でのオーナーシップを明確にできる**：マイクロサービスやドメインごとにイベントバスを分けることで、「このバスのイベントスキーマはこのチームが責任を持つ」という境界を技術的にも表現しやすくなります。

一方で、バスを分けすぎるとルールやターゲットの管理箇所が分散し、全体像の把握がかえって難しくなることもあるため、チーム構成やドメイン境界に合わせて適切な粒度で分割するのが実務上のポイントです。

### ルールとイベントパターン

受信したイベントのうち、どのイベントを処理対象にするかを「イベントパターン」として定義します。イベントの送信元サービスや、イベント本文の特定フィールドの値に基づいてマッチングさせることができます。時刻ベースで定期実行したい場合は、cron 式やレート式によるスケジュールルールも作成できます。

### ターゲット

ルールに一致したイベントの転送先です。Lambda 関数、Step Functions ステートマシン、SQS キュー、SNS トピック、Kinesis Data Streams、ECS タスクなど、多数のターゲットタイプがサポートされています。1 つのルールに対して複数のターゲットを設定することもできます。

## EventBridge Scheduler

cron 実行に特化した機能で、数百万単位のスケジュールされたタスクを、単一のルールに頼ることなく管理できます。1 回限りの実行や、繰り返し実行のスケジュールを、タイムゾーンを指定して柔軟に設定できます。既存のルールベースのスケジュール機能に比べて、大量のスケジュールジョブを扱う際のスケーラビリティに優れています。

## EventBridge Pipes

2 つのイベントソース（DynamoDB Streams、Kinesis、SQS、MSK など）とターゲットの間を、ポイントツーポイントで接続するための機能です。イベントのフィルタリング、変換（データのエンリッチメント）、ターゲットへの配信までを、Lambda を挟まずに宣言的に設定できます。

## SaaS 連携（パートナーイベントソース）

Datadog、PagerDuty、Zendesk、Auth0 といった SaaS ベンダーが発行するイベントを、パートナーイベントソースとして直接受信できます。自前で Webhook の受け口を実装しなくても、SaaS 側のイベントをトリガーに AWS 側の処理を起動できます。

## Amazon SNS・SQS との違い

いずれもメッセージング・通知の基盤として使われますが、役割が異なります。

- Amazon SNS：Pub/Sub 型の通知サービス。トピックを購読している複数の宛先へ、シンプルにメッセージをファンアウトする
- Amazon SQS：メッセージキューイングサービス。メッセージを一時的に保持し、コンシューマーが自分のペースで処理する
- Amazon EventBridge：イベントの内容（属性やペイロードの値）に基づいた高度なルーティングができる。SaaS 連携やスケジューリングなど、イベント駆動アーキテクチャ全体のハブとしての機能が豊富

シンプルな Pub/Sub であれば SNS、高度なイベントフィルタリングやルーティング、SaaS 連携が必要であれば EventBridge、という使い分けが一般的です。

## ユースケース

- マイクロサービス間の疎結合な連携（あるサービスの状態変化を、他の複数サービスに通知する）
- 定期バッチ処理のスケジュール実行（EventBridge Scheduler／ルール）
- SaaS からのイベントをトリガーにした自動化（インシデント発生時の通知フローなど）
- セキュリティイベント（GuardDuty の検出結果など）を受けて自動対処を行う仕組み
- DynamoDB や Kinesis のストリームデータを、Pipes 経由でフィルタ・変換して他サービスへ連携

## 料金

料金が発生するのは基本的にカスタムイベントバスへのイベント取り込みに対してで、AWS のサービスから発生するイベントの取り込みやルールの評価、ターゲットへの配信自体には EventBridge 側の料金は発生しません（ターゲット側のサービス料金は別途かかります）。EventBridge Scheduler は、月間一定回数までの無料利用枠を超えた呼び出し回数に応じて課金されます。最新の料金は [Amazon EventBridge の料金ページ](https://aws.amazon.com/eventbridge/pricing/) を確認してください。

## メリット

- サービス同士を直接連携させず、イベントバスを介して疎結合に保てる
- イベントパターンによる柔軟なフィルタリング・ルーティングができる
- SaaS との連携や大規模スケジューリングなど、周辺機能が充実している
- サーバーレスで、インフラ管理が不要

## デメリット・注意点

- イベントの配信順序は保証されない（順序性が必要な場合は SQS FIFO など別の仕組みが必要）
- イベントペイロードのサイズには上限があり、大きなデータそのものを流すのには向かない
- 複雑なイベントパターンやターゲットが増えると、どのルールが何を処理しているかの見通しが悪くなることがある
- 配信は基本的に At-least-once（重複配信の可能性がある）ため、受信側でべき等性を考慮する必要がある

## 📖 まとめ

Amazon EventBridge は、AWS サービス・自社アプリケーション・SaaS から発生するイベントを一元的に受け止め、柔軟なルールでルーティングする、イベント駆動アーキテクチャの中核サービスです。単純な通知には SNS、順序保証や再処理が必要なキューイングには SQS、というように役割の異なるサービスと組み合わせて使うことで、疎結合で拡張性の高いシステムを構築できます。
